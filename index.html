A. 경력 및 배경 이해 — Q1~Q3
Q1
현재 우리금융에서 하시는 업무를 구체적으로 설명해주세요.
경력 설명 · 현직 업무

우리금융그룹 계열 IT기업에서 AWS 기반 퍼블릭클라우드 도입 초기 멤버로 합류하여 네트워크 보안 아키텍처를 처음부터 설계하고 운영하고 있습니다.

첫째, AWS Network Firewall·WAF·Shield 등 핵심 보안 솔루션 설계를 Terraform으로 코드화하여, 모든 환경에서 동일한 보안 정책이 재현되도록 표준화했습니다.

둘째, Zero Trust 원칙 기반으로 망분리 구조를 설계하고, 금융 컴플라이언스 요건에 맞는 네트워크 통신 경로를 Python으로 자동 수집·분석하는 파이프라인을 구축해 수동 작업을 제거했습니다.

셋째, CSPM 감사 결과를 인프라 관점에서 인터뷰하고 조치하며, 재발 방지를 위해 Terraform 모듈에 선제 반영하는 역할을 담당하고 있습니다.

Network Firewall과 WAF 각각을 Terraform 모듈로 만들었습니다. 핵심은 "정책은 모듈 안에 고정, 환경별 차이는 변수(variable)로만 처리"하는 구조입니다.

Network Firewall 모듈에서 Stateless rule group에 기본 Deny All을 고정하고, 허용 CIDR·포트는 variable로 받도록 설계했습니다. WAF 모듈도 AWS Managed Rule Group(CommonRuleSet, SQLi, XSS)을 모듈 내에서 고정하고 서비스별 커스텀 룰만 variable로 받습니다.

GitLab CI/CD에 tfsec·checkov를 통합해서 모듈 자체에 취약 설정이 포함되면 배포 전 단계에서 자동 차단되는 구조도 함께 만들었습니다.
Q2
보안 엔지니어로서의 커리어패스를 설명해주세요.
커리어패스 · 인프라→보안 전환 배경

전환이라기보다는, 처음부터 인프라와 보안을 분리하지 않고 함께 다뤄온 방향입니다.

첫 직장인 Azure MSP에서 DDoS 공격 대응과 NSG 정책 관리를 인프라 엔지니어가 직접 담당해야 했습니다. 그때 네트워크 설계와 보안 정책은 별개가 아니라는 것을 실무에서 먼저 배웠습니다.

이후 게임사 멀티클라우드 인하우스에서는 인프라 엔지니어가 CSPM 감사까지 담당하면서 보안을 구조화하고 자동화하는 역량을 더 깊게 쌓았습니다.

인프라를 먼저 이해했기 때문에 보안 설계를 할 때도 운영 현실을 반영한 구조를 만들 수 있었다고 생각합니다.

부담이 전혀 없었다고 하면 거짓말이지만, 오히려 이 구조가 제 역량의 기반이 됐습니다.

보안팀이 별도로 있는 환경에서는 인프라와 보안이 분리되어 서로의 현실을 잘 모르는 경우가 많습니다. 저는 인프라를 직접 설계하면서 동시에 보안 취약점을 감사해야 했기 때문에, '이 설정이 왜 위험한지'를 인프라 레벨에서 정확히 이해하고 설명할 수 있는 능력이 생겼습니다.

결과적으로 보안을 별도 레이어로 얹는 게 아니라 인프라 설계 단계에서 자연스럽게 고려하는 방식으로 일하게 됐고, 지금 이 역량이 쿠팡에서도 그대로 발휘될 수 있다고 생각합니다.
Q3

그러나 실제 입사 후 퍼블릭클라우드 업무 비중은 20% 수준이었고, 나머지는 온프레미스 환경이 주를 이뤘습니다. 퍼블릭클라우드 인프라와 보안을 중심으로 경력을 쌓아온 저에게 이 환경은 성장 방향과 맞지 않는다고 빠르게 판단했습니다.

입사 기간이 짧다는 점은 인지하고 있습니다. 하지만 방향이 맞지 않는 환경에서 시간을 보내는 것보다, 퍼블릭클라우드를 대규모로 운영하는 곳에서 제 역량을 제대로 쓰는 것이 저와 회사 모두에게 더 맞다고 판단했습니다.

B. 기술 심화 — Q4~Q9
Q4
IAM 설계 시 가장 중요하게 고려하는 원칙과 실제 적용 사례를 말해주세요.
IAM · Least Privilege · SCP · Access Analyzer

가장 중요하게 보는 원칙은 Least Privilege(최소 권한)와 명시적 거부(Explicit Deny) 우선입니다.

게임사 멀티클라우드 인하우스에서 4개 CSP를 동시에 운영할 때, 서비스 계정과 역할을 Terraform으로 코드화하고 AWS에서는 SCP로 계정 레벨에서 특정 리전 외 리소스 생성과 MFA 없는 루트 계정 접근을 명시적으로 차단했습니다.

역할별 권한은 AWS Access Analyzer로 실제 사용 패턴을 분석하여 불필요한 권한을 주기적으로 정리하는 구조로 운영했습니다.

Access Analyzer가 하는 일: IAM 역할·정책을 분석해서 "실제로 지난 N일 동안 사용된 권한"과 "정책에 부여된 권한"을 비교해준다. 사용하지 않은 권한을 시각적으로 보여주기 때문에 "줄여도 되는 권한"을 정확하게 파악할 수 있다.

실제 사용 방식:
① IAM 콘솔 또는 Access Analyzer에서 각 역할(Role)의 "Last accessed" 정보를 확인
② 90일 이상 사용되지 않은 권한을 목록으로 추출
③ 해당 권한을 Terraform IAM 정책 코드에서 제거 → PR → tfsec 게이트 통과 후 배포
④ 분기마다 반복하여 권한 범위가 점진적으로 줄어드는 구조 유지

Q5
CSPM을 어떻게 활용했고, 오탐(False Positive) 처리는 어떻게 했나요?
CSPM · 리스크 판단 · Terraform 선제 반영

CSPM 도구 운영은 보안팀이 담당했고, 저는 보안팀이 도출한 감사 결과를 받아서 인프라 담당자로서 인터뷰를 진행하고 실제 조치를 수행하는 역할이었습니다.

첫째, 즉각적인 조치와 리스크 판단. 운영 중인 인프라에 바로 적용 시 서비스 영향이 발생할 수 있는 케이스는 차선책을 찾거나 다음 배포 주기에 맞추는 방식으로 리스크를 관리했습니다.

둘째, 반복 차단을 위한 Terraform 선제 반영. 한 번 지적된 취약점이 다시 발생하지 않도록, 다음에 구성하는 인프라의 Terraform 모듈에 해당 보안 요건을 미리 녹여두었습니다. 시간이 지날수록 CSPM 반복 지적 건수가 줄어드는 효과가 있었습니다.

CSPM 도구 운영과 CSPM 결과를 실제 인프라에 반영하는 것은 다른 역할입니다.

보안팀이 AWS Security Hub·GCP SCC로 결과를 도출하더라도, 그 결과를 인프라에 실제로 적용하고 재발을 막는 것은 인프라 담당자의 역할입니다. 저는 그 과정에서 어떤 취약점이 왜 발생했는지를 인프라 설계 수준에서 분석하고, 단순 조치에 그치지 않고 Terraform 모듈에 녹여서 구조적으로 재발을 차단하는 역할을 했습니다.

쿠팡에서는 CSPM 도구 운영까지 직접 담당하게 될 텐데, 결과를 해석하고 인프라에 반영하는 부분은 이미 익숙하기 때문에 도구 운영 자체는 빠르게 적응할 수 있습니다.
Q6
Terraform으로 보안 정책을 코드화할 때 어떤 방식으로 일관성을 유지했나요?
IaC · 모듈화 · tfsec · checkov · GitLab CI

핵심은 모듈화와 배포 전 자동 검증 두 가지입니다.

모듈화: Network Firewall·WAF·SG 표준 정책을 Terraform 모듈로 만들어 dev/stg/prod 모든 환경에서 동일한 코드를 사용. 환경별 차이는 variable로만 처리.

자동 검증: GitLab CI/CD에 terraform validate → tfsec → checkov를 필수 보안 게이트로 구성. SG에 0.0.0.0/0 인바운드가 포함되면 파이프라인이 자동 실패하여 배포가 차단됩니다.

Sentinel Policy 직접 운영 경험은 아직 없지만, tfsec·checkov 기반 policy-as-code 구조를 운영해온 경험이 있어 빠르게 적용할 수 있다고 판단합니다. 📚 tfsec/checkov 학습 →

좋은 지적입니다. 그래서 모듈 변경은 신중하게 다뤄야 합니다.

실제로는 두 가지 방식으로 관리했습니다. 첫째, 모듈 변경 전 반드시 terraform plan을 dev 환경에서 먼저 실행하여 변경 범위를 확인했습니다. 둘째, 보안 정책 자체의 변경(예: 새로운 위협으로 인한 룰 추가)과 환경별 설정 변경(CIDR, 포트)을 명확히 분리했기 때문에, 대부분의 환경별 변경은 variable 수정으로만 처리되어 모듈 자체를 건드리지 않았습니다.

모듈 변경이 불가피할 때는 GitLab CI의 tfsec·checkov 게이트를 통과한 후에만 배포가 가능하기 때문에, 변경으로 인한 보안 취약점 도입은 구조적으로 차단됩니다.
Q7
AWS Network Firewall rule group을 어떤 기준으로 구성했나요?
Network Firewall · Stateless/Stateful · 망분리

첫째, 트래픽 방향별 분리. 외부에서 들어오는 인바운드 트래픽, 내부에서 외부로 나가는 아웃바운드 트래픽, 그리고 내부 서버들끼리 주고받는 트래픽을 각각 별도 rule group으로 분리했습니다.

네트워크 트래픽을 방향으로 분류할 때 쓰는 용어다.

North-South 트래픽: 외부 인터넷 ↔ 내부 서버. 위아래 방향. 방화벽이 주로 통제하는 구간.
East-West 트래픽: 내부 서버 ↔ 내부 서버. 옆 방향. 예를 들어 웹 서버 → 앱 서버 → DB 서버처럼 내부끼리 주고받는 통신.

왜 중요한가: 침해된 서버 하나가 내부망을 타고 다른 서버로 이동하는 것을 "횡이동(Lateral Movement)"이라고 한다. East-West 트래픽도 방화벽으로 제어하지 않으면, 한 서버가 뚫렸을 때 내부 전체로 퍼질 수 있다. Network Firewall에서 East-West rule group을 별도로 두는 이유가 이 때문이다.

둘째, 변경 빈도별 분리. 거의 변경되지 않는 baseline 정책과 서비스별로 자주 변경되는 허용 규칙을 분리. 서비스팀 변경 요청이 전체 방화벽에 영향 주지 않는 구조입니다.

셋째, 금융 컴플라이언스 반영. Stateless rule로 기본 Deny All, Stateful rule에서 명시적으로 허용한 경로만 통과하는 구조로 설계했습니다.

전자금융감독규정 제15조 기준: 인터넷망 ↔ 업무망 ↔ 개발망 ↔ 관리망을 논리적으로 분리해야 합니다.

AWS에서는 VPC 분리 → TGW 중앙집중화 → Network Firewall Deny All → Stateful 허용 구조로 구현했습니다. TGW Route Table에서 인터넷망→업무망 라우트를 등록하지 않으면 통신 자체가 구조적으로 불가능해집니다.

Python 파이프라인으로 이 구조가 실제로 지켜지고 있는지 VPC 피어링·TGW 라우팅·SG 인바운드를 boto3로 주기적으로 수집하고 위반 시 Slack 알림 발송 구조도 구축했습니다. 📚 상세 보기 →
Q8
Zero Trust 모델을 실제로 어떻게 구현했나요?
Zero Trust · TGW · STS AssumeRole · CloudTrail

Zero Trust를 한 문장으로 정리하면 "위치가 아닌 자격으로 검증한다"는 원칙입니다. 세 가지 레이어로 적용했습니다.

네트워크 레이어: VPC 간 통신을 TGW를 통해 중앙집중화하고, SG는 CIDR 허용 대신 SG ID 참조 방식으로 구성하여 특정 리소스 그룹 간 통신만 명시적으로 허용.

IAM 레이어: 임시 자격증명(STS AssumeRole) 기반으로 장기 자격증명 사용을 제거. 서비스별 역할을 Terraform으로 코드화하고 최소 권한 원칙을 구조적으로 강제.

감사 레이어: CloudTrail·VPC Flow Logs·Firewall 로그를 Python 파이프라인으로 수집하여 이상 접근 패턴 자동 탐지.

STS(Security Token Service) AssumeRole: 장기 자격증명(Access Key ID + Secret) 없이 임시 자격증명을 발급받는 방식입니다.

예를 들어 EC2 인스턴스에서 S3에 접근해야 한다면:
— 기존 방식: EC2에 Access Key를 환경변수로 심어둠 → 키가 노출되면 영구적으로 탈취 가능
— AssumeRole 방식: EC2에 IAM Role을 부여 → EC2가 실행될 때 자동으로 임시 토큰 발급(1시간 유효) → 만료 후 자동 갱신

Zero Trust에서 핵심인 이유: 임시 토큰은 만료 시간이 있어서 탈취되더라도 피해 범위가 제한됩니다. 장기 자격증명이 없으면 '위치(IP)가 아닌 자격(Role)'으로만 접근이 허용되는 구조가 완성됩니다.
VPC Flow Logs는 VPC 내 네트워크 인터페이스를 통과하는 트래픽을 기록합니다. 여기서 주로 탐지한 패턴은 세 가지였습니다.

① 허가되지 않은 포트 스캔: 짧은 시간 동안 동일 Source IP에서 여러 포트로 REJECT 기록이 연속 발생하면 포트 스캔으로 판단
② 비업무 시간대 내부 통신: 야간·주말에 평소에 없던 내부 서버 간 통신이 발생하면 이상 징후로 탐지
③ 망분리 위반 경로: 인터넷망 VPC에서 업무망 VPC로 직접 트래픽이 기록되면 즉시 Slack 알림

Python으로 S3에 저장된 Flow Log 파일을 주기적으로 읽어서 이 패턴들을 필터링했습니다.
Q9
멀티클라우드 환경에서 보안 정책 일관성을 어떻게 유지했나요?
멀티클라우드 · Python 파이프라인 · 모듈화

CSP 네이티브 도구는 탐지 레이어로만 사용하고, 수집·분석·알림은 공통 Python 파이프라인으로 통합하는 구조를 선택했습니다.

AWS Security Hub, GCP Security Command Center, Azure Security Center 각각의 API로 감사 결과를 수집하되, 분석 로직과 Slack 알림은 단일 파이프라인에서 처리했습니다.

IaC 측면에서는 Terraform 멀티프로바이더를 활용하여 각 CSP의 보안 설정을 동일한 코드 스타일과 구조로 관리했습니다.

각 CSP의 API 응답 포맷이 달라서 이것이 핵심 도전이었습니다.

해결 방식은 추상화 레이어를 만드는 것이었습니다. 각 CSP별로 수집 함수를 따로 만들되, 반환 형식을 공통 딕셔너리 구조로 통일했습니다.

{ 'csp': 'aws', 'severity': 'HIGH', 'resource_id': '...', 'finding': '...' }

이 공통 구조로 변환한 뒤에는 분석·필터링·Slack 알림 로직이 CSP를 구분하지 않고 동일하게 동작합니다. 새로운 CSP가 추가되더라도 수집 함수만 추가하면 나머지 파이프라인은 그대로 재사용할 수 있는 구조였습니다.
C. 약점 방어 — Q10~Q11
Q10
Kubernetes/EKS 컨테이너 보안 실무 경험이 부족한데, 어떻게 기여할 수 있나요?
EKS · RBAC · PSS · Network Policy · 약점 방어

EKS 보안 실무 운영 경험이 부족한 것은 사실입니다. CKA 자격증 취득 과정에서 Kubernetes 아키텍처와 보안 개념은 학습했지만, 실제 프로덕션 환경에서 직접 운영해본 경험과는 차이가 있다는 점을 솔직하게 인정합니다.

다만 이렇게 생각합니다. 컨테이너 보안도 결국 세 가지 문제로 귀결됩니다. 누가 무엇에 접근할 수 있는지의 권한 문제, 어떤 트래픽이 허용되는지의 네트워크 문제, 그리고 정책을 코드로 강제하는 자동화 문제입니다. 이 세 가지는 제가 지금까지 해온 작업과 본질적으로 같습니다.

구체적으로 말씀드리면, Kubernetes에서 누가 어떤 리소스에 접근할 수 있는지를 정의하는 RBAC는 제가 AWS에서 설계해온 IAM 최소 권한 체계와 같은 원칙입니다. 역할을 세분화하고, 필요한 권한만 부여하고, Terraform으로 코드화한다는 흐름이 동일합니다.

네트워크 쪽도 마찬가지입니다. Kubernetes의 Network Policy는 Pod 간 통신을 허용·차단하는 규칙인데, 이것은 제가 Security Group에서 SG ID 참조 방식으로 특정 리소스 그룹 간 통신만 허용하던 방식과 개념이 같습니다. 어떤 워크로드가 어떤 워크로드와 통신할 수 있는지를 명시적으로 정의한다는 원칙이 동일합니다.

그리고 OPA/Gatekeeper는 제가 CI/CD 파이프라인에서 tfsec와 checkov로 구현했던 "배포 전 정책 게이트"를 Kubernetes 클러스터 안에서 그대로 구현하는 도구입니다. 배포 요청이 들어올 때 정책을 검사하고 위반 시 차단한다는 동작 방식이 완전히 같습니다.

EKS 실무 경험의 격차는 분명 존재하고, 입사 후 빠르게 따라잡아야 한다는 것을 알고 있습니다. 현재 CIS Kubernetes Benchmark와 AWS EKS 보안 가이드를 학습하고 있으며, 기존 인프라 보안 설계 역량이 컨테이너 환경에서 실질적인 기여로 이어질 수 있다고 생각합니다. 📚 K8s 구조 상세 학습 →

⚠️ 약점은 인정 → 구조적 근거 → 학습 중 순서로. "모른다"가 아니라 "기존 경험과 연결되는 이유"를 설명하는 게 핵심.
Q11
Terraform Sentinel Policy 경험이 없는데, 어떻게 적용할 계획인가요?
Sentinel · policy-as-code · tfsec · checkov

Sentinel Policy 직접 운영 경험은 없습니다. 다만 tfsec·checkov를 CI/CD 파이프라인에 통합하여 policy-as-code를 운영한 경험이 있어 Sentinel의 구조와 목적은 이미 이해하고 있습니다.

Sentinel은 Terraform Cloud·Enterprise에서 plan 결과를 기반으로 배포 전 정책을 강제하는 HashiCorp policy framework입니다. 제가 운영한 tfsec·checkov 게이트와 목적이 동일하고, rule 언어는 Terraform 실무 경험이 있으면 진입 장벽이 낮습니다.

합류 후에는 현재 tfsec·checkov 정책을 Sentinel rule로 마이그레이션하는 방식으로 빠르게 실무 적용이 가능합니다. 📚 tfsec/checkov 학습 →

Sentinel rule의 기본 구조는 다음과 같습니다:

import "tfplan/v2" as tfplan
main = rule { all tfplan.resource_changes as _, rc { rc.type != "aws_s3_bucket" or rc.change.after.acl != "public-read" }}

이 코드가 하는 일: Terraform plan에서 S3 버킷 변경 사항을 순회하면서, ACL이 public-read인 버킷이 있으면 배포를 차단합니다.

tfsec에서 aws-s3-no-public-buckets 규칙이 하는 것과 완전히 동일한 로직입니다. 제가 이미 이 규칙을 운영해봤기 때문에 '무엇을 검사해야 하는지'는 알고 있고, Sentinel의 문법만 익히면 됩니다. HCL과 유사한 문법이라 Terraform을 써봤다면 학습 곡선이 낮습니다.
D. 협업·문제해결 — Q12~Q15
Q12
보안 정책이 개발팀 배포 속도와 충돌했을 때 어떻게 해결했나요?
협업 · 커뮤니케이션 · 구조적 해결

"안 된다"고 말하기 전에, 왜 안 되는지를 먼저 설명하는 것이 가장 먼저 한 일입니다.

SG에 0.0.0.0/0 인바운드가 포함된 경우, "정책 위반"이 아니라 "이 설정이 배포되면 외부에서 해당 포트로 직접 접근 가능하고 금융 감사에서 지적 사항이 됩니다"라고 설명했습니다. 이유를 알면 대부분 협조적으로 수정해줬습니다.

같은 문제가 반복되지 않도록 자주 막히는 패턴은 Terraform 모듈에 미리 반영했습니다. 충돌을 줄이는 가장 좋은 방법은 보안 검토를 사후가 아닌 구조 안에 미리 녹여두는 것입니다.

이 상황에서 '보안이 항상 우선'이라고 말하는 것은 현실적이지 않습니다.

제가 기준으로 삼은 것은 리스크 레벨이었습니다. 외부 공개 서비스에 0.0.0.0/0 인바운드가 열리는 경우처럼 즉각적인 침해 가능성이 있는 HIGH 이상 취약점은 일정을 늦추더라도 먼저 해결했습니다. 반면 암호화 미설정이나 로깅 부재처럼 즉각적인 피해 가능성은 낮지만 감사 지적 가능성이 있는 MEDIUM 항목은 다음 스프린트에 반영하는 방식으로 타협점을 찾았습니다.

중요한 건 결정을 혼자 하지 않고 팀 내에서 리스크를 공유하고 함께 판단했다는 점입니다.
Q13
가장 기억에 남는 보안 사고 케이스와 대응 방식을 말해주세요.
DDoS · 자동화 대응 · 임계치 설정

MSP 재직 시 Mir4 Global(서버 3,500대) 운영 중 야간·주말에 집중적으로 발생하는 DDoS 공격이 가장 기억에 남습니다.

기존 수동 IP 차단 방식은 야간 공격에 대응 속도 한계가 있었습니다. Azure Log Analytics에서 DDoS Mitigation Flow Log를 주기적으로 조회하여, 비정상 TCP SYN 패킷 임계치를 초과한 Source IP를 자동 탐지하고 NSG Deny Rule에 즉시 등록하는 PowerShell 스크립트를 개발했습니다.

임계치 설정이 핵심이었습니다. 너무 낮으면 정상 트래픽 차단, 너무 높으면 대응 지연 — 실제 공격 로그를 분석하여 기준값을 설정하고 지속적으로 조정했습니다.

위협 대응에서 탐지보다 대응 자동화까지 설계해야 실질적인 방어가 된다는 것을 배웠습니다.

실제로 초기에 임계치를 너무 낮게 설정해서 정상 유저가 차단되는 사고가 있었습니다.

원인은 게임 이벤트 시간대에 트래픽이 평소의 3~4배로 급증하는 특성을 반영하지 않은 것이었습니다. 이후 두 가지를 보완했습니다. 첫째, 임계치를 시간대별로 다르게 설정했습니다. 이벤트 시간대는 기준값을 높이고, 야간에는 낮추는 방식입니다. 둘째, 자동 차단 전에 알림 전용 단계를 추가했습니다. 임계치 도달 시 바로 차단하지 않고 Slack 알림을 먼저 발송한 뒤, 담당자 확인 후 수동 또는 자동 차단이 이루어지도록 단계를 나눴습니다.

자동화는 사람의 판단을 완전히 대체하는 게 아니라, 사람이 판단할 수 있는 시간을 만들어주는 것이라고 배웠습니다.
Q14
쿠팡 규모의 환경은 지금까지 경험한 것보다 훨씬 크고 복잡한데, 어떻게 적응할 계획인가요?
규모 적응 · 학습 의지 · 기여 방향

규모가 커진다고 해서 보안 원칙 자체가 달라지지는 않는다고 생각합니다. IAM 최소 권한, 네트워크 분리, 정책 코드화, 자동화 기반 운영이라는 원칙은 규모에 무관하게 동일합니다.

다만 멀티 계정 관리, 대규모 EKS 환경, 다수 서비스팀과의 협업 등 제가 경험하지 못한 복잡도가 있습니다. 이 부분은 학습이 필요하다고 솔직히 인식하고 있습니다.

먼저 기존 구조를 빠르게 파악하고 현재 운영 방식을 이해하는 것을 우선하겠습니다. 이후 자동화·IaC 경험을 현재 구조에 맞게 기여하는 방향으로 접근할 계획입니다.

세 단계로 생각하고 있습니다.

첫 달 — 파악: 현재 AWS 계정 구조, VPC 설계, IAM 체계, 기존 Terraform 코드베이스를 파악합니다. 보안 이슈를 발견하더라도 먼저 전체 그림을 이해하는 것을 우선합니다.

둘째 달 — 기여: 파악한 구조 안에서 제가 기여할 수 있는 작은 부분부터 시작합니다. 기존에 없는 tfsec 규칙 추가, Terraform 모듈의 보안 요건 강화 등 코드 레벨에서 눈에 보이는 기여를 합니다.

셋째 달 — 확장: EKS 보안 설정, Sentinel Policy 적용 등 제가 아직 실무 경험이 부족한 영역을 팀원들과 함께 배우면서 역할을 넓혀갑니다.
Q15
보안 아키텍처를 설계할 때 가장 먼저 고려하는 것은 무엇인가요?
설계 원칙 · 위협 모델 · 운영 현실

가장 먼저 고려하는 것은 "무엇을 보호해야 하는가"입니다. 보호 대상과 그 가치를 먼저 파악해야 올바른 보안 수준을 설정할 수 있습니다.

이후 데이터 흐름을 파악하고, 외부에서 들어오는 접점, 내부 서버 간 통신, 권한 경계를 기준으로 위협 모델을 정의합니다. 그리고 탐지·예방·대응 레이어를 각각 어떻게 구성할지 설계합니다.

현실적인 제약도 항상 함께 고려합니다. 아무리 완벽한 보안 구조도 운영 가능하지 않으면 실제로 지켜지지 않습니다. 보안 수준과 운영 복잡도 사이의 균형을 팀과 함께 논의하며 결정했습니다.

공식 방법론(STRIDE, PASTA 등)을 엄격하게 따르지는 않았지만, 실무에서 자연스럽게 비슷한 흐름으로 진행했습니다.

STRIDE를 기준으로 설명하면:
S(Spoofing): IAM 자격증명 위변조 → MFA 강제, AssumeRole 기반 임시 자격증명
T(Tampering): 인프라 설정 변조 → Terraform 코드화 + Git 이력 관리
R(Repudiation): 행위 부인 → CloudTrail 전체 로깅
I(Info Disclosure): 민감 데이터 노출 → S3 퍼블릭 차단, 암호화 강제
D(DoS): 서비스 중단 → Shield, WAF Rate Limiting
E(Elevation): 권한 상승 → SCP, IAM 최소 권한

방법론을 알면 누락되는 위협 유형이 줄어듭니다. STRIDE는 면접에서 언급하면 좋은 키워드입니다.

Q16
보안 정책을 새로 도입할 때 조직의 저항이나 우선순위 충돌을 어떻게 해결했나요?
조직 설득 · 우선순위 · 리더십

보안 정책을 새로 도입할 때 가장 자주 마주쳤던 저항은 "왜 지금 해야 하나"라는 시급성의 문제였습니다. 특히 금융권에서 기존에 수동으로 처리되던 작업을 Terraform과 자동화로 전환할 때, 변화에 대한 불편함과 학습 비용 우려가 있었습니다.

제가 취한 방식은 두 가지였습니다. 첫째, 작은 단위로 먼저 보여주는 것이었습니다. 전체를 한 번에 바꾸려 하면 저항이 크지만, 한 모듈, 한 환경에서 먼저 적용해서 결과를 보여주면 설득이 훨씬 쉬워졌습니다. 둘째, 보안 정책 위반의 결과를 추상적인 리스크가 아닌 감사 지적, 장애 사례 같은 구체적인 언어로 설명했습니다.

보안은 강제로 도입하는 것보다, 함께 문제를 인식하게 만드는 것이 훨씬 오래 지속된다는 것을 배웠습니다.

실제로 금융권에서 Terraform 도입을 추진할 때 이 상황을 겪었습니다.

효과적이었던 접근 방식은 '비용'이 아닌 '리스크'의 언어로 설명하는 것이었습니다. '보안이 중요합니다' 대신 '이 설정이 감사에서 지적되면 어떤 영향이 생기는지'를 구체적으로 제시했습니다.

그리고 먼저 개인이 직접 작은 성과를 만들었습니다. 전체 인프라를 한 번에 코드화하려 하지 않고, 가장 자주 변경되는 SG 룰 관리부터 Terraform으로 바꿔서 배포 시간과 오류가 줄어드는 것을 수치로 보여줬습니다. 그 다음은 스스로 확산됐습니다.
Q17
클라우드 보안에서 가장 자주 놓치는 취약점이 무엇이라고 생각하나요?
보안 인식 · 실전 경험 · 통찰

제 경험상 가장 자주 놓치는 건 과도한 IAM 권한과 방치된 리소스입니다. 이 두 가지는 공통점이 있습니다. 처음엔 편의상 허용했다가 나중에 정리하지 않아서 누적된다는 점입니다.

IAM 쪽에서는 초기에 빠르게 작업하려고 폭넓은 권한을 부여한 뒤 줄이지 않는 경우가 많습니다. 서비스 계정에 AdministratorAccess가 붙어있거나, 특정 S3에만 접근해야 하는 역할이 전체 S3에 접근 가능한 상태로 방치되는 식입니다. AWS Access Analyzer로 이걸 정기적으로 감사해야 하는 이유입니다.

리소스 쪽에서는 개발·테스트 목적으로 열어둔 Security Group의 0.0.0.0/0 인바운드가 프로덕션까지 그대로 올라오는 경우가 생각보다 많았습니다. tfsec·checkov를 CI/CD에 붙인 이유 중 하나가 정확히 이 패턴을 자동으로 잡아내기 위해서입니다.

결국 보안은 한 번 설정하는 것이 아니라 지속적으로 확인하고 줄여나가는 과정이라고 생각합니다.

한 번 있었습니다. 정기 감사에서 90일 미사용으로 분류된 Lambda 실행 권한을 제거했는데, 해당 Lambda가 월 1회 배치 작업에서만 사용되는 것을 파악하지 못한 경우였습니다.

이후부터는 두 가지를 추가했습니다. 첫째, CloudTrail에서 해당 역할의 API 호출 이력을 90일이 아닌 최근 6개월로 확장해서 확인합니다. 둘째, 권한 제거 전에 해당 서비스 담당자에게 확인 메시지를 Slack으로 보내는 단계를 프로세스에 추가했습니다.

이 경험에서 배운 것은, 자동화 도구의 결과를 맹신하지 말고 항상 사람이 최종 판단하는 단계를 유지해야 한다는 점입니다.
Q18
AWS 멀티 계정 환경에서 보안을 어떻게 중앙에서 관리했나요?
AWS Organizations · SCP · Security Hub · 멀티 계정

현재 우리금융 환경에서 13개 AWS 계정을 운영하고 있습니다. 계정이 많아질수록 각 계정을 개별적으로 관리하면 반드시 정책 불일치가 생기기 때문에, 중앙 집중 관리가 필수입니다.

핵심은 AWS Organizations와 SCP(Service Control Policy)를 통한 계정 레벨 통제입니다. SCP를 사용하면 특정 OU(조직 단위) 아래 모든 계정에 대해 "서울 리전 외 리소스 생성 금지", "루트 계정 직접 사용 금지" 같은 정책을 구조적으로 강제할 수 있습니다. IAM 권한이 아무리 넓어도 SCP가 금지하면 실행 자체가 불가능합니다.

보안 상태 모니터링은 Security Hub의 통합 대시보드를 활용했습니다. 각 계정의 Security Hub 결과를 중앙 계정으로 집계하면 전체 계정의 보안 상태를 한 화면에서 파악할 수 있습니다. 여기서 나온 결과를 Python 파이프라인으로 수집해 Slack 알림과 연동했습니다.

IAM Policy: 특정 사용자·역할에게 "할 수 있는 것"을 부여하는 권한. 계정 내에서 동작.

SCP(Service Control Policy): AWS Organizations 레벨에서 계정 전체에 "절대 할 수 없는 것"을 강제하는 가드레일. IAM에서 허용되어 있어도 SCP가 Deny하면 실행 불가.

실무 활용 예시:
— SCP: "ap-northeast-2(서울) 외 리전에서 EC2 생성 금지" → 어느 계정, 어느 사용자도 도쿄 리전에 EC2를 만들 수 없음
— SCP: "CloudTrail 비활성화 금지" → 감사 로그 삭제를 구조적으로 차단

SCP는 "천장"이고 IAM은 "문"이다. 천장이 낮으면 문을 아무리 넓게 열어도 거기까지밖에 못 간다.

배포 전 코드 단계에서 보안 취약 설정을 자동으로 차단하는 도구들
왜 필요한가?
Terraform으로 인프라를 코드로 관리해도 보안이 자동으로 보장되지 않는다. 개발자가 실수로 S3를 퍼블릭으로 열거나, RDS 암호화를 빼먹거나, SG에 전체 오픈을 넣을 수 있다. 이 세 도구는 코드를 AWS에 배포(apply)하기 전에, 코드 단계에서 문제를 잡아낸다.
도구역할특징
terraform validate HCL 문법·변수 참조 오류 검사 AWS API 호출 없음. 보안 검사 X — 단순 문법 검사기
tfsec Terraform 코드 보안 취약 설정 정적 분석 AWS/GCP/Azure provider별 규칙 수백 개 내장. CRITICAL~LOW 심각도 분류. "티에프섹"
checkov CIS Benchmark 기반 더 넓은 범위 검사 Terraform 외 K8s YAML, Dockerfile, GitHub Actions도 지원. "체코프"

tfsec가 잡는 주요 항목 (AWS):

규칙 ID탐지 내용
aws-s3-no-public-bucketsS3 버킷에 퍼블릭 액세스 차단 설정 없을 때
aws-rds-enable-encryptionRDS 스토리지 암호화가 false일 때
aws-iam-no-policy-wildcardsIAM 정책에 Action: '*' 또는 Resource: '*' 있을 때
aws-cloudtrail-enable-all-regionsCloudTrail이 전 리전 로깅 안 할 때

GitLab CI/CD 파이프라인 통합 흐름:

Stage 1 — terraform validate
문법 오류 차단
실패 → 중단
Stage 2 — tfsec
CRITICAL/HIGH 보안 취약 설정 차단
실패 → 중단
Stage 3 — checkov
CIS Benchmark 기반 추가 검사
실패 → 중단
Stage 4 — terraform plan
실제 인프라와 비교, 변경 범위 확인
Stage 5 — terraform apply
main 머지 후, 모든 게이트 통과 시만 실행
# .gitlab-ci.yml stages: [validate, security, plan, apply] tf-validate: stage: validate script: - terraform init -backend=false - terraform validate tfsec-scan: stage: security script: tfsec . --minimum-severity HIGH allow_failure: false # CRITICAL/HIGH 발견 시 중단 checkov-scan: stage: security script: checkov -d . --framework terraform --quiet allow_failure: false
CI/CD 파이프라인에 terraform validate → tfsec → checkov → terraform plan 순서로 보안 게이트를 구성했습니다. PR이 올라오면 이 게이트가 자동으로 실행되고, SG에 0.0.0.0/0 인바운드나 암호화 미설정 같은 취약 설정이 발견되면 파이프라인이 중단되어 배포 자체가 차단됩니다. 보안 검토가 사람 손을 거치지 않아도 코드 레벨에서 자동으로 강제되는 구조입니다.
실제로 하나만 쓰는 곳이 더 많습니다. checkov 하나만 쓰거나, tfsec 하나만 쓰거나. 둘 다 쓰는 건 보안 성숙도가 높은 곳이나 대기업에서 주로 사용합니다.

면접 답변 포인트: "도구보다 중요한 건 배포 전 코드 단계에서 보안 취약 설정을 자동으로 차단하는 구조를 만들었다는 것입니다. tfsec/checkov는 그 구조를 구현한 도구의 예시입니다."
tfsec/checkov: 오픈소스. CI/CD 파이프라인에 직접 통합. 코드를 정적 분석.
Sentinel: HashiCorp 제품(유료). Terraform Cloud/Enterprise에서만 동작. plan 결과를 기반으로 정책을 강제함 — 더 세밀한 제어 가능.

목적은 동일: 배포 전에 정책 위반을 자동 차단. tfsec/checkov를 운영해본 사람이라면 Sentinel 적용이 어렵지 않다.
IAM
② AWS IAM Access Analyzer — 실제 사용 패턴 기반 권한 감사
불필요한 권한을 데이터 기반으로 찾아내고 최소 권한을 실현하는 도구
왜 필요한가?
IAM 정책을 작성할 때 처음부터 딱 맞는 최소 권한을 설정하기는 어렵다. 보통 처음엔 넉넉하게 주고 나중에 줄이겠다고 하지만, "나중에"는 잘 오지 않는다. Access Analyzer는 실제로 지난 90일 동안 사용된 권한을 AWS CloudTrail 로그 기반으로 분석해서, "이 역할이 실제로 쓴 권한"과 "정책에 부여된 권한"의 차이를 보여준다.

Access Analyzer가 하는 일 3가지:

기능설명활용
Unused access 분석 지난 90일간 사용되지 않은 IAM 권한, 역할, 액세스 키를 탐지 분기마다 스캔해서 불필요 권한 제거
External access 분석 S3 버킷, IAM 역할 등이 외부 계정이나 인터넷에 공개되어 있는지 탐지 의도치 않은 외부 공개 리소스 즉시 탐지
Policy validation IAM 정책 문법 오류, 과도한 권한 경고, 모범 사례 체크 정책 작성 시 실시간 검증

실제 사용 방식 — 단계별:

Step 1 — Analyzer 생성
IAM 콘솔 → Access Analyzer → Analyzer 생성 (계정 또는 조직 범위)
Step 2 — Unused access 리포트 확인
각 IAM 역할의 "Last accessed" 날짜 확인. 90일 이상 미사용 권한 목록 추출
Step 3 — 권한 제거 결정
미사용 권한 중 실제로 제거 가능한 것 선별 (서비스 영향도 확인)
Step 4 — Terraform 코드 수정
IAM 정책에서 해당 권한 제거 → PR → tfsec 게이트 → 배포
Step 5 — 정기 반복 (분기마다)
권한 범위가 점진적으로 줄어드는 구조. 한 번에 다 하려 하지 말 것.
# AWS CLI로 역할별 Last Accessed 정보 확인 # 어떤 서비스에 마지막으로 접근했는지 조회 # 1. 역할의 서비스 마지막 접근 날짜 조회 aws iam generate-service-last-accessed-details --arn arn:aws:iam::123456789:role/my-service-role # 2. 결과 확인 (job-id 사용) aws iam get-service-last-accessed-details --job-id xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx # 결과 예시: # ServiceName: Amazon S3 # LastAuthenticated: 2025-01-15T09:23:00Z ← 최근 사용 # ServiceName: Amazon DynamoDB # LastAuthenticated: None ← 한 번도 안 씀 → 제거 대상
Access Analyzer를 활용해서 각 역할이 실제로 지난 90일 동안 사용한 권한과 정책에 부여된 권한을 비교했습니다. 사용되지 않은 권한을 목록으로 추출한 다음, 서비스 영향도를 확인하고 Terraform IAM 정책 코드에서 제거했습니다. 이 작업을 분기마다 반복하면서 권한 범위가 점진적으로 줄어드는 구조를 만들었습니다. 사람이 판단하는 게 아니라 실제 사용 이력 데이터를 기반으로 하기 때문에 서비스 영향 없이 최소 권한을 구현할 수 있었습니다.
무조건 제거하지 않는다. 판단 기준이 필요하다.

제거 전 확인 사항:
— 해당 권한이 배치 작업이나 월별 작업처럼 주기가 긴 작업에 쓰이는 건 아닌지 확인
— CloudTrail에서 해당 서비스 API 호출 이력을 직접 조회해서 확인
— 개발·스테이징 환경에서 먼저 제거해보고 이상 없으면 프로덕션 적용

안전한 접근법: 한 번에 많은 권한을 제거하지 않는다. 한 역할당 2~3개씩 줄여가는 방식이 서비스 영향 없이 최소 권한을 달성하는 현실적인 방법이다.
K8s
③ Kubernetes 컨테이너 보안 — 구조부터 EKS까지
RBAC · Pod Security Standards · Network Policy · OPA/Gatekeeper · IRSA
핵심 개념 — Kubernetes는 왜 보안이 별도로 필요한가?

EC2: 서버 1대 = 워크로드 1개. 서버가 뚫려도 그 서버만 영향.
Kubernetes: 노드(EC2) 1대에서 수십 개의 Pod가 함께 실행. 보안이 잘못된 Pod 하나가 같은 노드의 다른 Pod, 또는 노드 OS 자체를 침해할 수 있다.

컨테이너 보안은 "VM 보안 위에 레이어를 얹는 것"이 아니라 별도로 설계해야 하는 이유다.

Kubernetes 전체 보안 구조 — 4개 레이어:

레이어 1 — 클러스터 접근 제어 (RBAC)
누가 쿠버네티스 API에 접근할 수 있는가? 어떤 리소스를 조작할 수 있는가?
레이어 2 — Pod 실행 보안 (Pod Security Standards)
컨테이너가 root로 실행되는가? 호스트 네트워크에 접근하는가?
레이어 3 — 네트워크 격리 (Network Policy)
어떤 Pod가 어떤 Pod와 통신할 수 있는가?
레이어 4 — 배포 정책 게이트 (OPA/Gatekeeper)
허가된 레지스트리 이미지만 배포 가능한가? 필수 레이블이 있는가?
레이어 1 — RBAC 구조 (IAM과 같은 원칙):

— Role: 특정 Namespace 안에서 허용되는 동작 정의
— ClusterRole: 클러스터 전체 범위의 허용 동작 정의
— RoleBinding: 사용자/ServiceAccount에게 Role 부여
— ClusterRoleBinding: 클러스터 전체 범위로 ClusterRole 부여

위험 패턴: verbs: ["*"] 또는 resources: ["*"] — 와일드카드 권한. AWS IAM에서 Action: '*'와 동일한 리스크. 탈취 시 클러스터 전체 장악 가능.
위협설명
Privilege Escalation컨테이너가 root 권한으로 실행되면, 탈출(escape) 시 노드 OS 전체 장악 가능
Host Namespace 접근hostNetwork: true 설정 시 노드 네트워크에 직접 접근, 다른 Pod 트래픽 도청 가능
Writable Filesystem파일시스템 쓰기 가능 시 악성코드 심거나 설정 파일 변조 가능
Secrets 노출환경변수로 Secret 주입 시 env 명령으로 누구나 조회 가능

Pod Security Standards (PSS) 3단계:

레벨대상주요 제한
Privileged 시스템 컴포넌트 (kube-system) 제한 없음. CNI, CSI 드라이버용. 일반 앱 절대 사용 금지
Baseline 일반 애플리케이션 privileged: true 금지, hostNetwork/hostPID 금지, 위험한 capabilities 금지
Restricted 보안 민감한 서비스 Baseline 포함 + root 실행 금지(runAsNonRoot: true 필수) + seccomp 프로파일 필수

Pod Security Standards는 IAM 최소 권한 원칙의 컨테이너 버전입니다. OPA/Gatekeeper는 제가 CI/CD에서 tfsec·checkov로 구현한 '배포 전 정책 게이트'를 Kubernetes 클러스터 레벨에서 동일하게 구현하는 도구입니다. 정책을 코드로 정의하고 위반 시 자동 차단한다는 원칙은 완전히 같은 맥락입니다.
PSS 먼저, OPA/Gatekeeper는 그 다음.

PSS는 Kubernetes 내장 기능이라 별도 설치 없이 Namespace에 레이블만 붙이면 바로 적용 가능. 기본 보안 baseline을 빠르게 구성하기 좋다.

OPA/Gatekeeper는 "우리 회사 내부 레지스트리에서만 이미지를 가져와야 한다" 같은 커스텀 정책이 필요할 때 추가로 도입. 설치와 정책 작성 비용이 있지만 훨씬 세밀한 제어 가능.
Pod가 AWS 서비스(S3, DynamoDB 등)에 접근할 때 Node의 IAM Role을 공유하면 안 된다. Node Role에 S3 권한이 있으면 그 Node의 모든 Pod가 S3에 접근 가능해지는 문제가 생긴다.

IRSA(IAM Roles for Service Accounts): Pod가 AWS 서비스에 접근할 때 Node IAM Role을 공유하지 않고 Pod 단위로 별도 IAM Role을 부여하는 방식.

문제 상황: Node에 S3 읽기 권한이 있으면 그 Node의 모든 Pod가 S3에 접근 가능 → 침해된 Pod가 S3 전체 데이터를 탈취 가능
IRSA 해결: system:serviceaccount:prod:app-sa처럼 특정 Namespace의 특정 ServiceAccount만 해당 Role을 맡을 수 있도록 OIDC 조건을 걸어둔다.

이것이 IAM 최소 권한 원칙을 컨테이너 환경에 그대로 확장 적용하는 것. AWS IAM에서 역할별 권한을 코드화했던 경험이 여기서 동일하게 적용된다.

ZT
③ Zero Trust 구현 — 3개 레이어
네트워크 · IAM · 감사 레이어로 "위치가 아닌 자격으로 검증"
네트워크 레이어
TGW 중앙집중화 + SG ID 참조 방식 (CIDR 허용 대신)
IAM 레이어
STS AssumeRole 임시 자격증명 + Terraform 코드화된 최소 권한
감사 레이어
CloudTrail + VPC Flow Logs + Python 파이프라인으로 이상 탐지
CIDR 방식: 10.0.1.0/24처럼 IP 대역을 허용. 해당 대역의 모든 IP가 허용됨. 서버가 늘어나거나 IP가 바뀌면 관리 어려움.

SG ID 참조 방식: sg-xxxx처럼 특정 Security Group을 소스로 허용. 그 SG에 속한 리소스만 접근 가능. IP가 변해도 SG 멤버십이 유지되면 자동으로 적용.

Zero Trust 원칙에 더 부합함: IP 위치가 아닌 "어떤 리소스 그룹에 속해 있는가"라는 자격으로 검증.
